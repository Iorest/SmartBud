# 记账口径：一条记录到底算进哪里

这份表是各子功能共用的"费用口径"矩阵。改任何一处统计前先看这里，否则很容易出现
「账户余额对得上、统计对不上」或者「昨天小计和本月合计互相矛盾」。

**本文只回答"算不算费用"。现金流与净资产是另外两个口径，为什么这么分、退款/坏账/分期的
目标规则，见 [accounting-conventions.md](accounting-conventions.md)。**

## 一行的身份

`TransactionModel` 只有三种特殊身份，其余都是普通收支：

| 身份 | 字段 | 记账含义 |
|---|---|---|
| 普通支出 | `income = false` | 真的花掉了 |
| 普通收入 | `income = true` | 真的赚到了 |
| 报销支出 | `reimbursable = true`（`reimbursedAt` 表示已回款） | 垫付，钱会回来 |
| 报销回款 | `income = true` + `reimbursementOf = <报销支出的 id>` | 公司/同事把钱还回来 |
| 余额调整 | `adjustment = true` | 只是把账面数字改对，不是消费 |

待实现的三种身份——退款（冲减原支出，不得记为收入）、坏账（核销为费用）、
分期本金/利息（本金不进费用、利息进费用）——规则见
[accounting-conventions.md](accounting-conventions.md) 第 2 节。在它们实现之前，
不要用"记一笔收入"来模拟退款，也不要用删行来处理不回款的报销。

**报销是一对两行，不能只有一半。** 只标记「已报销」而不记账，账户余额会永远少那笔钱；
只记一笔收入而不标记，收入会凭空多出来。所以核销时由 `ReimbursementLedger` 自动写入
回款行（金额、账户、基准币金额都与原支出一致），撤销核销时把这一行删掉。

一笔转账不是交易，单独存在 `TransferModel`：钱从 A 到 B，属于账户间移动。
**但手续费是支出**：建转账时会在转出账户上自动写一条「手续费」支出行（`transferFeeOf`
指回转账），所以手续费进支出统计、预算和分类占比，而转账本身仍然不进收支。
转账的 `fee` 字段只用于显示，`outgoingTotal` 只有 `amount` —— 否则同一笔 2.50 会被扣两次。

## 影响面

| 用途 | 普通支出 | 普通收入 | 报销支出 | 报销回款 | 余额调整 | 转账 |
|---|---|---|---|---|---|---|
| 账户余额 | 计入 | 计入 | **计入**（钱确实出去了） | **计入**（钱确实回来了） | **计入** | 转出扣 `amount`，转入加 `receivedAmount`；手续费由独立支出行扣 |
| 支出统计 / 分类占比 / 柱状图 | 计入 | — | 不计入 | 不计入 | 不计入 | 转账本身不计入；**手续费行计入** |
| 收入统计 | — | 计入 | — | **不计入** | 不计入 | — |
| 净收入（收入 − 支出） | 计入 | 计入 | 不计入 | 不计入 | 不计入 | 不计入 |
| 预算剩余 | 计入 | — | 不计入 | 不计入 | 不计入 | 不计入 |
| 流水日小计 | 计入 | 计入 | 0 | 0 | 0 | 0 |
| 「待报销」卡片 | — | — | 未回款的计入 | — | — | — |
| AI 账单分析 | 计入 `totalSpent` | 计入 `totalIncome` | 单独字段 `pendingReimbursement` | 不计入 | 不计入 | 不计入 |
| 小组件 | 同 App | 同 App | 不计入 | 不计入 | 不计入 | 不计入 |

一对报销的净效果永远是 0：账户 −88 再 +88，支出和收入都不变，日小计也不变
（流水里两行加起来正好抵消）。

实现上只有三个判定，全部在 `TransactionModel` 的扩展里：

```swift
countsAsSpend   // !income && !adjustment && !reimbursable
countsAsIncome  // income && !adjustment && !isReimbursementIncome
signedBaseAmount // 收入 +base，支出 -base，其余 0
```

**所有统计代码都必须走这三个判定**，不要再手写 `!$0.income` —— 那正是
「报销混进支出」「余额调整拉高收入」的来源。

报销的一对行由 `Services/ReimbursementLedger.swift` 维护：核销写入回款、撤销删除回款、
编辑任一半同步另一半、删除原支出连带删除回款、删除回款把原支出放回「待报销」。
SQL 侧的 `#Predicate` 同样不能表达 `reimbursementOf != nil` 之外的组合，所以那里直接
取所有回款行再在内存里比较 id。

例外只有一处：SwiftData 的 `#Predicate` 不能调用计算属性，预算明细的查询里
必须把三个标记写全：

```swift
!$0.income && !$0.adjustment && !$0.reimbursable
```

改动其中任何一个标记时，记得同步 `FilteredBudgetViews` 里的谓词。

## 金额的两个版本

- `amount`：账户币种下的原值。跨币种账户里它就是外币金额。
- `baseAmount`：记账当时按汇率折算的基准货币金额，**冻结**。

所有跨账户、跨期的合计一律用 `wrappedBaseAmount`（取 `baseAmount`，旧数据退回 `amount`），
这样改汇率不会让历史统计漂移。

舍入：最小单位是分，折算四舍五入（half-up）；多币种先各自折算再求和，尾差挂当期最大项。
切换基准币会重述全部历史 `baseAmount`，属于一次性操作，必须留审计记录才能解释历史数字。

## 转账手续费

`fee` 记在转出账户的币种上，但它只是展示值：真正的钱由一条独立支出行承担
（`transferFeeOf` 指向转账，带分类、计入支出统计与预算）。转出方余额
= `amount` + 手续费行，转入方 = `receivedAmount`；`outgoingTotal` 只返回 `amount`，
所以手续费不会被扣两次。

信用卡还款也是转账（信用卡 → 储蓄账户），不是支出：记成支出会把同一笔钱算两次——
一次是刷卡时的消费，一次是还款。`kind = credit` 的余额为负表示欠款。

删掉那条手续费行时，`TransferFeeLedger.detachFeeRow` 会把转账的 `fee` 归零——
`migrate` 靠 `fee > 0` 判断是否需要补行，不归零就会在下次启动把用户删掉的费用复活。

## 未来记录

`date > now` 的记录是"待发生"：流水把它们放在 UPCOMING 分区，统计、分类占比、
图表、预算一律不计（统一 `date <= now`）。账户余额目前仍按实际余额计算，
不因未来记录提前扣减。

## 跨功能约定

- **删除**：删账户 → 交易保留、清空归属，相关转账与它们的手续费支出行一并删除；
  删分类 → 交易保留、清空分类与备注中的分类名副本，关联预算一并删除。
- **报销配对**：任何删除入口（单条、批量、侧滑暂存）都必须先走
  `ReimbursementLedger.prepareForDeletion`：删报销支出带走回款行，删回款行把支出
  退回待报销。批量把已核销的报销移到收入分类时先 `unsettle`，否则回款会留在账上。
- **归档**：不进默认账户列表、不计总资产、不能作为新记账的默认账户或转账端点，
  但历史交易、转账、报表照常解析。
- **隐藏**：不进列表、不计总资产，也不做默认账户；「已隐藏」分组里可以恢复，
  否则隐藏等于不可逆的数据黑洞。
- **撤销删除**：`TransactionSnapshot` 必须保存编辑器能写的所有字段，包括
  `reimbursementOf` / `transferFeeOf`，否则撤销出来的回款行会被当成普通收入。
  （账户、baseAmount、折扣、报销、调整）—— 少一个字段，撤销就会悄悄改掉余额。
- **导入**：按 id 合并；导入后要刷新账户、分类、统计、小组件四处缓存。
