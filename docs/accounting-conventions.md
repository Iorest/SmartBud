# 记账口径的会计基础

[ledger-rules.md](ledger-rules.md) 回答"这一行算进哪里"，这份文档回答**"为什么这么算"**。
两份冲突时，以本文的会计基础为准，然后同步修 ledger-rules。

## 1. 记账基础：个人收付实现制

SmartBud 是个人记账，采用**收付实现制（cash basis）**：钱动了就记，没动就不记。
不采用权责发生制（accrual），因为没有应收应付的账期管理需求，引入应计会把"记一笔账"
变成"做一笔分录"，违背"3 秒记完"的产品前提。

由此推出**三个口径必须分开报**，混用是绝大多数"对不上"的来源：

| 口径 | 回答的问题 | 包含什么 | 不包含什么 |
|---|---|---|---|
| 现金流 | 这个月我的钱净变化多少 | 所有让账户余额变化的行（含报销垫付、回款、调整） | 未来记录、已删除记录 |
| 个人费用 | 这个月我自己花了多少 | 普通支出 + 手续费 + 坏账核销；退款按负向冲减 | 报销垫付、报销回款、余额调整、转账本金 |
| 净资产 | 我现在有多少钱 | 资产账户余额 − 负债账户余额 | 预算、待报销（属应收，另列） |

**报销就是三个口径分叉的典型**：垫付 88 元，现金流 −88，个人费用 0，净资产 −88 且多了一笔
88 元的应收。现在的 UI 只在"账户余额"体现现金流、在"支出"体现费用，没有单独展示应收，
所以用户会觉得"我明明少了 88，支出却是 0"。这是已知的表述缺口，见第 6 节。

## 2. 一行的身份

现有五种（`ledger-rules.md` 有完整矩阵）：

| 身份 | 判定 | 现金流 | 费用 |
|---|---|---|---|
| 普通支出 | `!income && !adjustment && !reimbursable && refundOf == nil` | − | + |
| 普通收入 | `income && !isReimbursementIncome` | + | −（负向） |
| 报销支出（垫付） | `reimbursable = true` | − | 0 |
| 报销回款 | `income && reimbursementOf != nil` | + | 0 |
| 退款 | `refundOf != nil`（`income = false`） | + | −（冲减） |
| 余额调整 | `adjustment = true` | ±（按差额） | 0 |
| 坏账核销 | `badDebtOf != nil`（`income = false`，**无账户**） | 0（钱从没动） | + |

已核销的报销支出本身仍是"报销支出"，只是退出待报销列表（`badDebtAt != nil`）。

**待实现**的身份，规则先定在这里，实现前不得用其他方式绕：

| 身份 | 目标规则 | 为什么不能凑合 |
|---|---|---|
| 分期本金/利息 | 本金是负债减少，**不计费用**；利息与手续费**计费用**；末期尾差归最后一期 | 把整期还款当支出会重复计本金，12 期下来总支出虚高一倍 |

## 3. 退款与坏账（已实现）

- 身份：`refundOf = <原支出 id>`，`income = false`，金额为正，统计时按负向冲减原分类
  （`TransactionModel.spendBaseAmount` 在退款行为负）。退款**不计入收入**。
- 三要素对齐 iCost：退款金额、到账时间、到账账户；**到账时间不得早于原支出时间**。
- 可多次部分退，累计不得超过原额。**已退金额不另存字段**：由所有 `refundOf` 指向该行的
  退款金额求和得到（`RefundLedger.refundedTotal`），删掉一条退款后剩余额度自动回来，
  不会出现"计数器与真实行不一致"。
- 跨币种：退款按原支出的冻结汇率折算（`baseAmount / amount × 退款金额`），不按退款当天
  汇率——否则一次退款会改写历史统计。因此退款的到账账户必须与原支出同币种，换币种请先转账。
- 已退满额后再退：拒绝并提示，不允许负支出（`RefundPolicy.validate`）。
- 退款与预算：冲减到账当期的预算消耗与分类占比（费用口径），但不退现金流到原月份
  （现金流按到账日，账户余额在到账账户上加回）。
- 删除原支出会连同它的退款行一起删除（`RefundLedger.prepareForDeletion`）；删除单条退款
  只影响剩余额度。退款行在流水里可编辑（金额/日期/账户），走 `RefundSheet`，
  不走普通记账表单。

### 坏账核销

- 身份：`badDebtOf = <待报销支出 id>` 的**费用行**（`income = false`），原因存在
  `badDebtReason`（`BadDebtPolicy.Reason`：`unreachable` / `rejected` / `companyClosed` / `other`）。
  原行**不删不改金额**，只在 `badDebtAt` 记下核销日，从而退出待报销列表。
- 门槛：垫付满 **90 天**（`BadDebtPolicy.thresholdDays`）才可核销，按自然日算；
  未满时拒绝并给出剩余天数。太早核销等于鼓励用户放弃还在路上的钱。
- 金额：核销行取原行的**基准币金额**（冻结汇率），不是原币金额。核销行不对应任何账户，
  所以它不参与账户余额、也不出现在账户流水里——钱当天没有动，只是承认它回不来了。
- 费用：核销行计入支出统计、分类占比与预算（继承原行分类，归核销当期）；原垫付行仍不计费用。
  净收入与流水日小计按支出侧看到这条损失，因此"支出 +100"与"净收入 −100"同时成立，
  而账户余额一分未变。
- 撤销：删除核销行即把原行放回待报销；删原行连带删除核销行；原行不再标记为垫付时
  （清掉 `reimbursable` 或改成收入分类）核销行一并删除。
- 已核销的垫付不能再标记"已回款"：钱要么回来，要么核销，先撤销核销
  （`TransactionViewModel.setReimbursed` 里是硬性 guard）。
- 编辑原行金额会同步核销行金额（`BadDebtLedger.sync`），但**核销日期不变**——改金额不该
  把损失挪到另一个月。
- 部分核销（只承认损失一部分）未实现；当前是整笔核销，部分回款请先按实际金额记退款/回款。

## 4. 分期与负债（设计目标，未实现）

- **分期**：`InstallmentPlanModel` 同时存本金、手续费/利息、期数、首期日。
  每期生成两行或一行带拆分：本金部分不进费用，利息部分进费用；末期 `本金 − 已分摊本金` 全部归入，
  保证逐分相等。
- **提前结清**：只结清已发生利息，未发生利息不确认（个人记账不做折现）。
- **信用卡**：`AccountKind.credit` 的余额为负表示欠款；**还款是转账**（信用卡 → 储蓄账户），
  不是支出，也不是收入。额度与账单日尚未建模（`creditLimit`、`statementDay` 未实现）。
- **净资产**：`Σ(资产余额) − Σ(负债余额绝对值)`；信用卡欠款天然为负，加总即减。
  待报销的应收单独统计，不混进净资产，避免"钱没回来但净资产已经变好"。

## 5. 预算：信封法，不结转

- 预算 = 一段时间内的费用上限；周期结束剩余**不结转**，超支显示负数并保留记录。
- 按费用口径统计：普通支出计入，退款负向冲减（到账当期），报销垫付与回款都不占额度。
  这仍是费用视角的选择，代价是"垫付很多但预算没动"（退款则是"买过又退了，额度回来"）。
  如果以后要"现金流预算"，应新增独立预算类型，不要改现有口径（改口径会让所有历史预算数字变化）。
- 预算锚点独立于 `firstDayOfMonth`：可以从 6 月 15 日开始一个 30 天周期。

## 6. 舍入、尾差与重述

- 金额最小单位是**分**，模型存 `Double`（历史原因），所有展示与比较前先量化到分；
  折算一律**四舍五入（half-up）**，不用银行家舍入——用户对"四舍五入"的预期更强。
- 多币种合计：**各自折算后求和**，不要先求和再折算；尾差挂到当期金额最大的那一项，
  并在导出里保留原始 `amount`。
- **切换基准币是一次性重述**：所有历史 `baseAmount` 乘同一个汇率，之后不再变。
  重述必须留审计记录（时间、旧基准、新基准、汇率、影响行数），否则半年后无法解释
  "为什么 3 月的数字和当时截图不一样"。当前只有折算、没有审计记录，属实现缺口。
- 汇率来源优先级：手动设置 > 网络更新（Frankfurter/ECB）> 上次缓存；缺汇率时拒绝折算，
  不允许按 1:1 猜。记账、编辑、调整余额、深链、CSV 导入这些写入口在
  `CurrencyRateStore.needsRate` 为真时直接拒绝（提示去「设置 → 货币 → 汇率」补）；
  JSON 的交易行本来带导出时冻结好的 `baseAmount`，只有旧备份的手续费补写可能缺汇率，
  此时跳过该行、等下次启动 `TransferFeeLedger.migrate` 再补，不写猜测值。
  `CurrencyConversion.rate` 的 1 兜底只用于只读合计与转账建议，不再落到任何 `baseAmount`。
  判定统一由 `CurrencyConversion.needsRate` 给出：汇率缺失或存了 0、负数、非有限值都算缺。

## 7. 对账与调整

- `adjustment` 是"账面修正"，不是消费。**每次调整应带原因**（记错、漏记、银行手续费、
  其他），否则无法复盘；当前只有调整行、没有原因字段。
- 调整金额 = 用户看到的实际余额 − 系统算出的余额；调整后两者必须相等
  （实现见 `AccountViewModel.adjustBalance`；当前没有覆盖这一不变量的测试）。
- 期初余额不可被调整改写；调账永远新增一行，可删除、可追溯。

## 8. 一致性测试要求

每个口径至少一条测试，且测试名必须写清口径（不要叫 `testStats`）：

- 现金流：报销垫付 + 回款后，账户余额回到原值，流水日小计为 0。
- 费用：报销不占支出与预算；退款冲减原分类；坏账核销进费用（且不动账户余额）。
- 坏账：`BadDebtPolicyTests` 钉 90 天门槛与拒绝原因；`BadDebtLedgerTests` 钉"核销后
  支出 +base、账户余额不变、撤销后回到待报销"。
- 净资产：信用卡欠款为负、还款为转账、总资产含负债。
- 舍入：跨币种合计的尾差归属稳定；同一笔数据重复计算结果一致。
- 重述：切换基准币后，历史统计与导出金额可解释（有审计记录）。

## 9. 与参考产品的关系

iCost 的公开信息只有官方帮助文档（闭源，无公开代码），可对标的是**行为**：
退款三要素、分期账单日与额度恢复、多账本、标签与附件、日历与地图。
凡是本文与 iCost 行为冲突的，以本文为准并在 [icost-parity.md](icost-parity.md) 记录偏差理由。
