# 与 iCost 的能力对照

## 先澄清一件事

iCost 是**闭源**产品，没有公开代码仓库。能参考的只有它的官方帮助文档
（`help.icostapp.com`，英文站导航 57 个条目）和 App 的实际行为；社区里存在
第三方导入/MCP 工具，那是逆向它的数据文件，不是它的实现。所以本文对标的是
**能力与交互结果**，不涉及它的代码结构，也不复制它的界面。

"看账的入口"（日历、地图、标签、多账本）。AI 录入是唯一比 iCost 更靠前的一块，
但它的准确率基线还低（见 [ai-eval.md](ai-eval.md)），不能当卖点吹。

## 值得借鉴的交互

这些是 iCost 文档里写明的行为，判断对我们有用才拿：

1. **智能记账的输入约束**：必须包含金额 + 事项描述，否则不识别。我们照做，
   比"什么都接、什么都猜错"可靠。
2. **按卡号后四位/关键词匹配账户**：截图里出现"招商银行(4132)"就选尾号 4132 的账户。
   我们目前靠用户选，命中率不如它；TELE-18 可加这条规则。
3. **秒开模式**：打开即记账页。我们已有。
4. **模板 + URL Scheme**：外部触发记账。我们已有。
5. **退款三要素**：金额、到账时间、到账账户，且时间不得早于原账单——这是防错设计，
   直接采纳。
6. **分期账单日生成 + 已执行期数**：允许补录历史期数，避免用户从第 6 期开始用时
   前 5 期是空的。我们的 TELE-29 已包含。
7. **报销与退款分离**：iCost 把报销（钱会回来）和退款（钱退回来但交易取消）分开建模，
   我们不合并这两种身份。

## 明确不跟的地方

| iCost 做法 | 我们不做的理由 |
|---|---|
| 用无障碍服务在后台识别第三方 App 账单页 | 隐私风险高，且 iOS 上无法实现同等机制 |
| 识别走服务端并要求定位权限 | 账单截图含姓名、卡号；我们坚持端侧 OCR |
| 会员分层到"多账本/导出" | 导出属数据可携性（GDPR 20 条），收费会同时招致审核与合规质疑 |
| 无广告、无社区的买断承诺 | 与我们的 Pro 订阅模型不同，避免照抄承诺 |

## 演进顺序（与任务表一致）

1. 先把"钱的身份"补全：退款 → 部分报销 → 分期 → 坏账。
2. 再补"看账入口"：标签/附件 → 日历/地图 → 多账本。
3. 最后才是跨端与可穿戴。

理由：身份不全会让统计长期不可信，入口只是便利性；先修账，再加窗。
