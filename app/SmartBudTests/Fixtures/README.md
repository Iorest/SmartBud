# 记账语料库

给智能记账解析用的可回归语料与标注规范。目的是让后续任何规则/模型改动都有量化依据，而不是靠手感。

- `corpus_text.json`：600 条文本短语（500 条中文 + 100 条英文）
- `corpus_receipts.json`：200 条截图 OCR 文本
- `validate_corpus.py`：校验脚本，只用 Python 标准库

本目录不含产品代码。Swift 测试可用 `#filePath` 相对定位读取，无需改 `project.pbxproj`：

```swift
let fixtures = URL(filePath: #filePath).deletingLastPathComponent().appending(path: "Fixtures")
```

## 字段说明

### `corpus_text.json`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | `text-0001` 形式，全库唯一。`text-0001`–`text-0500` 为中文块，`text-0501`–`text-0600` 为英文块（其中 17 条含中文商户名，用于中英混说）。 |
| `text` | string | 用户原话，保留口语省略、数字与空格。 |
| `amount` | number | 用户实际付出/实际到账的金额，两位小数以内，`0 < amount <= 100000000`（`Money.maxAmount`）。 |
| `currency` | string | ISO 4217 三字母代码。无货币符号或写 `元`/`yuan` 时为 `CNY`。 |
| `direction` | string | `expense` 或 `income`。 |
| `category` | string | 必须落在现有 10 个桶：餐饮、交通、购物、咖啡、娱乐、通讯、教育、医疗、工资、奖金。 |
| `merchant` | string \| null | 文本明确出现商户/品牌时给规范化名称；泛称或未提及为 `null`。 |
| `note` | string \| null | 只记影响理解的歧义（多金额、约数、退款、数字不是金额等）；无歧义为 `null`。 |

### `corpus_receipts.json`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | `rcpt-001` 形式，全库唯一。 |
| `lines` | string[] | 按截图从上到下逐行抄录的 OCR 文本，非空。 |
| `amount` | number | 最终支付金额（纸质小票取「合计」）。 |
| `merchant` | string | 收款方/店名，非空。 |
| `platform` | string | `alipay`、`wechat`、`paper` 三者之一；当前数量 70 / 70 / 60。 |

## 采集口径

- **来源**：全部为自拟合成语料，不来自任何真实用户日志或截图。句式覆盖中文记账口语（「早饭15」「满100减20」「10.25 午饭 35」）、支付平台文案和常见英文说法。
- **规模**：中文 500 条、英文 100 条；小票 200 条。分类分布以日常支出为主，餐饮/购物/交通占比最高，收入（工资、奖金）约 11%。
- **金额**：全部虚构，按类别量级做偏态分布（多数为日常小额，少量大额），不代表真实定价。
- **商户**：知名品牌与虚构小店混用；不含真实姓名、地址、卡号、手机号、订单号。订单号一律写成 `****`，仅用于测试解析器忽略干扰行。
- **隐私红线**：不写任何真实个人身份信息；`validate_corpus.py` 内置手机号、银行卡号、身份证号、邮箱正则扫描，命中即失败。

## 标注规则

分类口径以 `ExpenseTextParser.bucketKeywords` 为准，是产品既定分桶而不是语义最优。常见归属：奶茶/咖啡豆 → 咖啡；健身、电影、KTV、会员 → 娱乐；超市、日用品、水果 → 购物；宽带、话费 → 通讯；体检、药店 → 医疗；教材、网课 → 教育；工资、奖金是收入桶。

### 金额

1. **取实际支付/到账金额**。原价、优惠前金额、赠送金额、余额、找零都不是 `amount`。
   - `满100减20 买了件卫衣实付80` → 80
   - `充话费 100 送20` → 100
   - 小票 `合计 130.00 / 实收 132.00 / 找零 2.00` → 130（消费总额；实收和找零是支付过程信息）
2. **日期、时间、数量不是金额**。
   - `10月25日 午饭 35` → 35
   - `打车 3 个人 88` → 88（3 是人数）
   - `2杯咖啡 实付35.50元` → 35.5（2 是杯数）
   - `10.25 午饭 35` → 35（10.25 是日期）
   - `停车 2小时 10块` → 10（2 是时长）
3. **口头约数按说出的数字标**，`note` 注明「口头约数」：`大概35 晚饭` → 35。
4. **AA/分摊只标自己承担的部分**：`午饭35，AA后我付17.5` → 17.5。
5. **多金额取最终支付额**，`note` 写清原价/优惠：`原价120 优惠券20 实付100 火锅` → 100。

### 方向

- 退款、报销到账记为 `income`，`category` 保留原消费类别（餐饮/交通/购物/教育等），不归到工资或奖金；`note` 注明原因。这与现有解析器把所有含「退款/报销」的句子判为收入的约定一致。
- 工资、奖金两个桶只能出现 `income`；校验脚本会拒绝这两个桶里的 `expense`。
- 收入类文本不得使用「花费/cost me」等支出措辞，应写成「工资到账 15600.32」「annual bonus 5000」。

### 商户与币种

- `merchant` 只在文本明确出现商户/品牌时填写，并做规范化：中石化 → 中国石化、大麦 → 大麦网、电信 → 中国电信。泛称（面馆、超市）或未提及一律 `null`，不做无依据推断。
- 币种跟随文本中的符号：`$` → USD、`£` → GBP、`HK$` → HKD；无符号或 `元`/`yuan` → CNY。
- 中英混说按语义标注，不因语言切换改变分类或方向（如 `lunch 35元` → 餐饮/expense/CNY）。

### 小票

- `lines` 逐行抄录，保留余额、优惠、订单号等干扰行——它们正是解析器要忽略的内容。
- `amount` 取最终支付金额；纸质小票取「合计」。
- `merchant` 取收款方/店名；纸质小票的商品必须与该店相符（健身房小票不出现电影票）。

## 校验

```bash
python3 app/SmartBudTests/Fixtures/validate_corpus.py
```

通过时输出（退出码 0）：

```
text corpus: 600 entries, 600 unique (600 ids)
receipt corpus: 200 entries, 200 unique (platforms: alipay, paper, wechat)
PII scan: 2 files, 0 hit(s)

OK
```

校验内容：

- 条目数：文本 600、小票 200；id 唯一且格式正确。
- 字段齐全且无多余字段；类型正确；`merchant`/`note` 可为 `null` 但不可为空串。
- `amount > 0`、不超过 `Money.maxAmount`、最多两位小数，并且**该数值必须能在 `text`/`lines` 中以数字形式找到**（防止金额与文本不一致）。
- `direction`、`platform`、`currency` 取值合法；小票三种平台都有样本。
- `category` 落在 10 个桶内；工资/奖金只能是收入。
- 去重：文本按小写、空白折叠后唯一；小票按行拼接后唯一。脚本打印的唯一数必须等于条目数。
- PII：对两个 JSON 和本 README 扫描手机号、银行卡号、身份证号、邮箱，命中即失败。

## 人工复核记录

- 时间：2026-10-30
- 抽样：`random.Random(20261031)` 随机抽 50 条文本 + 20 条小票，逐条核对 `amount`、`direction`、`category`、`merchant` 与文本语义是否一致。
- 结论：最终版本 50/50 文本一致、20/20 小票一致，**误标率 0%（< 2%）**。
- 复核中发现并已修正的生成缺陷（修正后重抽复核通过）：
  1. 金额写进文本时小数被截断（文本 `¥186`，标注 `186.09`）。校验脚本因此新增「金额必须出现在文本中」检查。
  2. 英文模板把商户和事项硬拼，出现 `健身房 movie ticket` 这类矛盾。
  3. 纸质小票把同一大类下的任意商户与商品组合，出现「健身房卖电影票」「地铁自助机卖汽油」；已改为按店铺给商品。
  4. 工资模板与「本月工资」条目叠加，生成 `本月上月工资` 的语法冲突；已删去带月份前缀的条目。

复现抽样（在仓库根目录）：

```bash
python3 - <<'EOF'
import json, random
entries = json.load(open("app/SmartBudTests/Fixtures/corpus_text.json"))
for e in random.Random(20261031).sample(entries, 50):
    print(e["id"], e["text"], e["amount"], e["direction"], e["category"], e["merchant"])
EOF
```

## 扩展方式

- 追加条目时使用新 id，不改动已有 id；文本一旦修改，要同步 `amount` 并重跑校验。
- 新增分类需要同时改 `ExpenseTextParser.bucketKeywords` 与本脚本的 `CATEGORIES`，两处保持一致。
- 新增小票请保持 `lines` 与 `amount` 一致，并保留余额/优惠等干扰行。
- 不修改 `project.pbxproj`：测试通过 `#filePath` 读取本目录。

## 已知限制

- 语料是合成的，覆盖的是常见说法与边界写法，不等同于真实用户输入的完整分布。
- 金额只保证与文本一致且在合理量级内，不追求逐项真实定价。
- 标注只覆盖 10 个现有分类桶；新增分类或解析器口径变化时，需要重新标注受影响条目。
